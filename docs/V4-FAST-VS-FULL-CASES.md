# 中文 v4 快速与完整轮数：两例真实会话分析

结论：这次“快速更快、成品也更好”的反馈有明确过程依据。完整轮数付出了稳定的额外准备等待，但大半追加调用没有产出可用方向；它又放大了 v4 把旧工具报错反复当作当前反证目标的缺陷。不能由两例推出低档普遍胜过高档。另发现一处可复现的证据接口接线错误，应优先于继续增加轮数处理。

## 1. 身份与比较口径

- 快速：session-74675d8e-6deb-4dd4-b643-9c97c9489b00，产物 [mbt-leviathan.html](<D:/0中转站/html/mbt-leviathan.html>)。
- 完整轮数：session-6b096f71-1321-4056-af8e-4feee5698532，产物 [mbt-ultra-photoreal.html](<D:/0中转站/html/mbt-ultra-photoreal.html>)。
- 两者真实用户任务逐字相同，均中文、hybrid 3+3、推理协议4、deepseek-account/deepseek-flash，**实际工作生成都是 max、maxTokens256000**。快并非因主模型降档。方向则是快速 off/1024，完整 low/4096；这次同时改变方向档位与追加轮次。
- 每次普通工作生成前触发一组增强。58/68次含提供商失败重试，成功公开assistant消息50/61条；不要把所有增强组数都算作有产物进展的步骤。

完整追加轮按尝试次数为第1轮58、第2轮25、第3轮2；按实际可用方向为第1轮25、第2轮2、第3轮0。“actualRounds=3”只说明尝试到了，不等于完成了三轮有效改进。“完整”这个称呼在当前预算下高估了实际有效过程。

完整轮数方向等待比快速多23.32分钟，而主模型累计时间反而少8.59分钟。不同内容、工具间隔与传输错误会影响净总耗时，不能简单相减当成单一模式因果增益；但新增方向准备开销本身可由调用时间戳直接定位。两例所有主生成失败都是DeepSeek Messages TRANSPORT，不是成品错误。

## 3. 为什么更多方向没有稳定变成更好的成品

**追加方向改进没有带来新的现实观测。** 引擎在一组开始时快照一次证据/公共上下文，追加轮只在同一上下文上看此前建议、再写一份建议，期间没有工具执行。它增加的是解释和文字，不是三轮“改代码→实际测试→修复”。27条有效追加方向只是通过内容过滤，不代表27项质量改善。

**两例均被工具失败记忆带入长期反证模式。** 快速51/58组、完整61/68组为diagnose；其待核对项全部是invocation-failure，而非已确认的成品失败。不存在Chrome路径、编辑old_string不匹配、验证脚本语法错，都会持续作为明确引用背景。两例同有这个问题，不是完整独有。

完整的E385/E387尤其有说明力：seq385故意执行ZZ_SENTINEL_ZZ→相同字符串，seq387故意执行ZZ_ABSENT_ZZ→ZZ_REPL_ZZ，以负向对照核对工具报错。模型随后数次解释它们是主动探针，但末段方向仍把E387解读为“预期修改可能没落地”，并要求逐项审计。交付present后又进行17项修改落地审计，增加的是程序文本核对而非画面效果。快速交付后也多了2条台账说明，不能把快速说成没有此开销。

**v4存在实际接口错误。** [evidenceSnapshot](../po06/lib/inference-boost.js#L89-L96)保留recentEvidence；[evidenceData](../po06/lib/inference-directions.js#L126-L163)只遍历openIssues/observations，忽略recentEvidence。实际快照隔离复现：旧E387仍进入专门证据节选，新E421（SELF.fails=0、facts12、exit0）没有进入；仅在内存将同一真实观测别名映射到observations后就出现。未修改生产代码。

这不是说E421可替E387关闭——它们检查不同对象/结果，不能洗白旧失败；问题是“近期做了什么、哪些已经检查”的正式证据通道没有送到方向模型。同时kind/pendingReason中的invocation-failure/not-a-product-check也没作为原始性质送入节选，条目统一成kind:issue。近期结果仍可能存在于被截断的公共历史中，因此不能说模型完全看不见新结果；能确定的是专门接口丢字段、背景严重偏向旧失败。

## 4. 成品反馈为何能落到具体过程差异

快速实际跑通了Edge/WebGL2、真实UV与倒角对照、浏览器模块加载、WebGL画布取图和合成键盘监听器。根据真实截图修地面高光、天空反射、尘埃和闪光；根据实际输出修stray `>` 和键盘注入定时竞态。最终有[实物截图](<D:/0中转站/html/.mbtv2/final_hero.png>)以及hits KeyW/KeyD、dpos3.96m、dyaw0.915等直接结果。不是没有错误，而是错误被真实产物反馈带回修复。

完整轮数的Edge尝试多次超时/访问被拒，后续主要转向CDN检查、Node几何构造、坐标不变式和桩化DOM/WebGL六帧。它确实修掉了SELF方法this丢失、部分尺寸与测距假数据等真实问题，不能称额外思考全无价值；但最终诚实承认“真实浏览器首帧/着色器/PMREM未观察”。一串静态/桩测试无法提供真实材质、构图、光照或手感的反馈，所以不如快速那样形成画面迭代。

我复跑了完整成品原样SELF+CFG片段，12项记录、fails0，sponsonHalf1.81与反推下限1.81相等。最终答复里的“下限1.855”是过时文字，不据此伪造成品数值缺陷。本轮未重新渲染完整作品，视觉优劣以用户实际体验为准；我仅查看了快速原会话保留图片，不用源码评审冒充双图视觉对照。

## 5. 归因与下一步建议

能确定：完整方向准备更慢，追加方向有效率低；同一现实证据上重复改写的轮次不是执行纠错轮次；正式近期证据字段丢失；旧调用错误缺少“已解释/预期负向探针/不再影响主任务”的可引用状态；快速的真实产物反馈链比完整充分。

不能确定：low方向本身导致画质差、完整轮数必然伤害模型、快速在所有任务都更好。这两例大幅重叠并发运行，工具调用标志、依赖路线也不同：快速离线内联r161且启用no-sandbox/disable-gpu，完整CDN r160及addons、浏览器标志与策略不同。完整声称“本机Edge不可用”不能推为全局事实，快速同机实际跑通了。未发现足够证据证明两会话互相干扰进程。

建议当前把快速当实际开发的基线，而不是为了“更强”强上完整轮数。下一次改动优先补齐recentEvidence与错误性质接口，区分“保留真实失败记录”和“每步继续追查它”；让故意负向探针和已解释但不再影响产物的调用错误不再持续驱动diagnose。真正尚未修复的成品失败必须继续保留，不是删掉失败让面板变绿。

额外轮次应为明确未决问题提供不同且可执行的区分观察，并在实际执行获得新信息后更新，而不是常态化把同一材料再写几遍。不建议直接加时限/预算或恢复独立裁判。若将来要隔离轮次本身的收益，需固定方向off/同一依赖与运行通道，只改变是否追加轮次；本轮只分析，不擅自修改设置或实施新机制。
