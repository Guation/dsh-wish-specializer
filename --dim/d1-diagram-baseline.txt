## 数据流的四条链路

**写链路（同步部分）**：`客户端 JSON → 网关鉴权后转内部 DTO → 服务校验+领域逻辑 → ORM 实体 → SQL 落 MySQL`。
**写链路（异步部分）**：MySQL 事务提交的同时把领域事件写入 outbox 表，CDC 读 binlog 投到 Kafka，下游 Worker 消费。
> 关键点：业务代码**只写库，不双写 MQ**。outbox + CDC 保证“数据落库”与“事件投递”原子，避免“库成功、消息丢”的不一致。

**读链路**：请求 → 网关 → 服务 → 先查 Redis（cache-aside）→ 命中直接返回；未命中回源 MySQL 从库 → 回填缓存（带随机 TTL 防雪崩，空值缓存防穿透）。搜索类走 ES，不查主库。

**分析链路**：binlog → Kafka → 数据湖（原始事件，不可变）→ ETL → 数仓 → BI。全链路以 binlog 为唯一事实源，业务代码不需要为报表额外埋点。

## 各环节数据形态

| 编号 | 形态 | 说明 |
|---|---|---|
| ①② | JSON/HTTP | 外部契约，版本兼容，不暴露内部字段 |
| ③ | Protobuf/DTO | 内部契约，与外部解耦 |
| ④ | KV 字节串 | 序列化对象，TTL 秒级 |
| ⑤ | 关系行 + 事务 | 强一致边界 |
| ⑥⑦ | 事件（含 event_id、聚合根 id、版本号） | 不可变事实 |
| ⑨⑩ | 事件 → 文档 | 消费者幂等，按 event_id 去重 |
| ⑫⑬ | 分区文件（Parquet） | 列式，按天分区 |

## 关键代码：outbox 与幂等消费

```python
# 写：同一本地事务内落库 + 落事件
def create_order(cmd):
    with db.transaction() as tx:
        order = tx.insert("orders", cmd)              # ⑤
        tx.insert("outbox", {                          # ⑥
            "event_id": uuid4(),
            "aggregate_id": order.id,
            "type": "OrderCreated",
            "version": order.version,
            "payload": json.dumps(order.to_dict()),
            "status": "NEW",
        })
    return order

# CDC 投递（Debezium 读取 outbox 表变更 → Kafka topic order.events）

# 消费：至少一次投递 + 幂等落库
def consume(msg):
    evt = json.loads(msg.value)
    with db.transaction() as tx:
        if tx.exists("consumed", evt["event_id"]):   # 去重
            return
        if tx.get_version(evt["aggregate_id"]) >= evt["version"]:
            return                                    # 乱序保护
        tx.apply(evt)
        tx.insert("consumed", evt["event_id"])
```

## 需要讲清的三条规则

1. **同步链路只做“必须立刻知道结果”的事**，通知、积分、索引全部异步，缩短 RT 并隔离故障。
2. **跨服务的数据一致性靠事件 + 幂等 + 版本号**，不靠分布式事务；消费端允许重复、不允许错序。
3. **数据只能沿一个方向流动**：业务库 → binlog → 事件总线 → 下游。下游禁止反写业务库，避免环状依赖。
