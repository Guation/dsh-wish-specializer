## 系统架构图：数据流向视图

以「电商交易 + 数据消费」为原型。读者定位：**工程评审**，所以标出数据形态变化与落点；如果给非技术决策者看，删掉 Kafka、CDC、ODS 三层术语，只保留「接入 → 业务 → 存储 → 加工 → 消费」五个方框即可。

### 图例（先看图例再看图）

| 视觉语言 | 含义 |
|---|---|
| 粗实线 `==>` | 同步请求/响应，在线链路，有超时和重试 |
| 虚线 `-.->` | 异步消息/事件，解耦、可重放 |
| 虚线 + `T+1` / `回流` 标签 | 批量或反向回写，非实时 |
| 黄色圆柱 | 消息中间层（易漏画的中间环节） |
| 紫色圆柱 | 持久化落点，括号内标数据形态 |
| 灰色虚线框 | 系统边界外或支撑旁支（降级层） |

### 顺着读一遍（主链路 5 跳）

1. **采集**：用户端经网关进来（原始请求），第三方回调走异步通知到同一入口——入口只有一处，边界与「外部」一眼可辨。
2. **在线处理与落库**：网关分发到业务服务，订单服务写 MySQL 形成**事务记录**（正向写入），同时写 Redis 缓存、附件落对象存储。这一步是「内存 → 持久化」的形态转移。
3. **变更外发**：订单服务发事件、MySQL 走 CDC 捕获变更，两路汇入 Kafka，统一成**规范化事件流**。这里是旁支最容易漏的中间环节：事件不是日志，是可重放的中间态，必须画出来。
4. **加工**：Kafka 一路进 Flink 做实时清洗聚合，落数仓（ODS 明细 → DWD 宽表 → DWS 指标）、回写 ES 索引与 Redis 实时指标；另一路 T+1 由 ETL 从主库抽全量装载数仓，并**回流**对账差异到订单服务。
5. **消费**：数仓对 BI、下游订阅方输出；特征回流推荐、标签回流用户服务；运营后台读缓存并反向写回订单服务。

### 三条容易被画错、这里刻意区分开的流

- **同步 vs 异步**：实线只有 4 段（网关到三个服务、服务到主库），其余全是虚线。看图的粗线数量就知道强耦合点在哪、扩容和熔断要保护谁。
- **正向写入 vs 回流**：所有回指左侧的线一律带「回流 / 对账差异」标签，避免误读成主链路，误以为服务之间是单向依赖。
- **实时 vs 批量**：Flink 与 ETL 是两条并行加工线，共用数仓落点但时延语义不同，所以必须并排而不是合流。

### 验收

不讲解，只看图能否答上：数据从哪来（U/T → GW）、经过谁（服务 → MQ → Flink/ETL）、存在哪（MySQL/Redis/ES/对象存储/数仓各自存什么形态）、被谁用（BI/推荐/运营/订阅方）、出错或回流走哪条路（死信重放、对账回流）。五问答齐即合格；若某条线只能靠口头解释，那它就还缺一个标签或一个中间节点。
