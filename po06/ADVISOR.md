# 顾问系统（2026-10-20 重构）

顾问是**流程里的点拨节点**，不是验收闸门。它只在三个位置被叫：

| 入口 | 什么时候用 | 内部对应 |
|---|---|---|
| `understand` | 不明白怎么做 | develop_approach 提示词 |
| `improve` | 自评不过关、想再抬一档 | improve_result |
| `rework` | 返工、同一条路反复失败 | diagnose_failure |
| `verify` | 只核对**已声明**的验收项 | review_result |

旧的 `mode` 仍可用（兼容别名），新调用建议直接传 `entry`。

## 它怎么说话

两段式，上限 **512 token**：

```
【顾问的理解】
现在……，是因为……，所以你应当……

【具体建议】
1. ……
2. ……

【交付判断】证据齐全，可以交付。 / 还不能交付：… / 有证据拿不到，先问用户：…
```

三条硬规则：

1. **不写施工图**：代码块、行内代码、命令行、数值参数、操作步骤一律不出现在建议里；
2. **不写祈使命令**：`必须修/必须执行` 这类前缀会被剥掉——建议是建议；
3. **超 512 token 先砍例子**，保住"病因 + 最关键一条"。

## 台账（每轮先结旧账）

- 会话级，最多 20 条未结项；
- 每次调用顾问前，把【你上次留下的未结结论】塞进提问；
- 顾问必须逐条回 `resolvedClaims: [{id, status: resolved|obsolete|unknown, note}]`，**不许沉默跳过**；
- 哈希只作提示（"这些文件变了"），是否失效由顾问判断；
- 关掉开关即清账。

## 交付闸门

| 证据状态 | 动作 |
|---|---|
| 全部 satisfied | 可以交付 |
| 有 failed | 先改，不许交付 |
| 有 unverified 且 impact/severity=major | **调 ask 问用户**（选项：接受风险 / 先补证 / 换口径） |
| 有 unverified 但影响小 | 标注后放行 |

没有 checks 时按 verdict 兜底：`unverified` ⇒ 问用户，`gaps` ⇒ 先改。

## 开关关掉

整条流程退化成线性：不调用顾问、注入文里不出现顾问块、台账清空。
拦截（优化→确认/跳过）与顾问始终是两个系统，互不阻塞。
